# Code audit, 2026-11-16: Optimize, cable routing, cable display

Scope: the Optimize pipeline end to end (`store.optimizeLayout` -> `calculateOptimalLayoutJoint`
-> greedy placer -> `calculateRoutingCost` -> `routeCablePaths` -> lane router / strategy cascade
/ A*), plus what the canvas and panels show for it. Nothing in `src/` was changed.

Ordered by what it costs to be wrong. Every number below was measured this session by running
the real engine, not read off the code.

## How it was measured

- **Baseline:** `npm test` 548 passed / 4 skipped, `tsc --noEmit` clean, `eslint` clean, `knip`
  clean, before and after the audit.
- **Corpus:** 216 boards. The 66 `config-matrix` scenarios, plus 150 seeded random boards on four
  real board sizes (Classic Jr, Classic 2, Classic Pro, Wide 22) at 45-80% row fill, 4-15 pedals,
  mixed side-jack and top-jack pedals. Each went through normalize -> optimize -> apply (exactly
  as the store applies it) -> derive.
- **NOT in the corpus: the real saved boards.** `dump-configs-offline.js` failed with
  `fetch failed` (no database access from this sandbox). So no figure here is about J$ Home or
  `test`. Re-run the fingerprint on them before acting on a percentage.
- Timing is node, inline, not the browser worker.
- The harness was throwaway vitest files, removed from the repo afterwards. Copies and raw output
  are in the session scratchpad (ephemeral). Each finding says how to reproduce it.

## What held

- 0 of 216 optimized boards had overlapping or off-board pedals.
- 1 invalid cable in 1,962 drawn.
- Scored length == drawn length on every board, when both are given the same pedal array
  (the P1.5 parity holds at the router level).
- Determinism held everywhere it was checked.

## 1. The same board draws two different ways (and Optimize reports the one you do not see)

**Root cause: `cables/routing-strategies.ts:469-480`.** The `channel` rung sorts boxes by top edge
and takes the gap between *consecutive* boxes. Two pedals in one row with different depths (any
rotated pedal, any EQ-200) tie on `top`, so which gap is found depends on the order of the
`placedPedals` array. In one order the real corridor is found; in the other the "gap" lands
inside the deeper pedal, the rung fails, and the cable falls through to A* or the perimeter.

Minimal repro (three boxes, one cable, only the array order differs):

    order A,B,C: strategy=channel  14.3in  (-50,100)->(-50,223.5)->(300,223.5)->(300,300)
    order B,A,C: strategy=astar    19.9in  (-12,100)->(-12,-12)->(300,-12)->(300,300)

**Why it reaches the user: `store/configuration-store.ts:837-844`.** The optimizer scores each
candidate with the array in chain order (`layout/index.ts:1200`). The store then writes new
`chainPosition` values without re-sorting the array. So when Optimize changes the order, the
canvas routes a different array than the one that was scored. Through the real store:

    rand#1057 (Classic Pro, 13 pedals)
    Optimize summary says            after = 40.73
    drawn right after Optimize       73.2in, 2 crossings   (wrap cable goes around the board)
    drawn after normalizeChain()     30.7in, 0 crossings   (pedal state byte-identical)

Any later `normalizeChain` or a save-and-reload (`load-configuration.ts:103` orders by
`chain_position`) re-sorts the array and the cables jump with nothing moved.

Measured: 18 of 216 boards draw differently under a shuffle of the array (8 by more than 0.5in,
worst 45.2in vs 72.6in). 3 of 216 had an Optimize score that the applied board does not have.

### FIXED 2026-11-16 (same day, uncommitted at time of writing)

`freeBandsBetween` in `cables/routing-strategies.ts` merges overlapping y-ranges into occupied
bands and proposes a channel only in the free space between two bands. A union cannot depend on
how ties were ordered. Nothing else changed - the store still does not re-sort, and does not
need to.

Re-measured on the same 216 boards, this time against eight permutations per board (store
order, reversed, six seeded shuffles) rather than the single shuffle above:

| | before | after |
|---|---|---|
| boards that draw differently by array order | 30 | 0 |
| Optimize score != applied board's score | 3 | 0 |
| total drawn length | 11,551in | 11,512in |
| crossings | 128 | 121 |
| invalid cables | 1 | 1 |
| lane violations | 4 | 6 |

**The lane-violation row is a real cost, and it is a separate weakness this fix exposes rather
than one it creates.** Both new violations are on one board (`rand#1047`), which Optimize now
lays out differently (score 181.29 -> 126.58): two cables take the same row corridor, it is too
narrow for two lanes, and they are drawn on the same line for 60px. The cost function has no
term for overlapping runs, so the optimizer cannot see that when it picks the layout. Not chased
here - it is open, and the config-matrix corpus (which asserts zero lane violations) is unaffected.

Regression tests, both run against the old code first to confirm they fail there (7 of 14 red:
`expected 99.20 to be close to 40.73`, `expected 'astar' to be 'channel'`, three matrix boards
differing when the array is reversed):

- `cables/__tests__/routing-order-independence.test.ts` - permutes the pedal array on eight
  matrix boards (three of which were order-dependent) and compares the drawn cables; plus the
  three-pedal repro above in every order of the three.
- `store/__tests__/optimize-draws-what-it-scored.test.ts` - the 13-pedal board through the real
  store: the summary's score equals the applied board's score, and `normalizeChain` does not
  change the drawing.

Suite: 562 passed / 4 skipped (was 548), `tsc`, `eslint`, `knip` clean.

## 2. The shopping list and the cable total are not the cables on screen

`cables/index.ts:19,223-246` computes every cable's length as straight-line jack distance x 1.2,
rounded up to a standard length. "What to buy" (`cable-list-panel.tsx:77`), the toolbar total
(`board-readout.tsx:57`), the right panel (`right-panel.tsx:73`) and the dashboard
(`dashboard/page.tsx:76`) all read that estimate. The routed path is never consulted.

- 165 of about 1,330 pedal-to-pedal cables were drawn longer than the length the list says to buy.
- Worst: a perimeter cable drawn at 55.4in, listed as a 12in patch cable.
- Board totals disagree in both directions: readout 174in vs 113.2in drawn; readout 60in vs
  75.6in drawn.
- Optimize's own summary ("12in less cable length") is a third number, from routed length.

Fix: derive list length from the routed path (`RoutedCable.path`), then round up. The estimate
can stay as the fallback for a cable that failed to route.

## 3. The lane router draws about 50% more cable than the cascade, and wins every tie

`route-cables.ts:348-349` routes each board twice and keeps the lane version unless the cascade
has strictly fewer *crossings*. Length, validity and lane spacing are not compared.

Same 216 final boards, each router on its own:

| | lane router | strategy cascade |
|---|---|---|
| total drawn length | 14,228in | 9,365in |
| fewer crossings on | 28 boards | 88 boards |
| lane violations (runs <9px apart) | 8 | 4 |
| invalid cables | 1 | 1 |

On the 100 boards where crossings tie, the lane version was more than 3in longer on 93 (mean
+19.4in), and on all 93 the cascade had zero lane violations. The cascade was no worse on
crossings, validity and lane spacing *and* shorter on 179 boards; the lane router on 2.

One board, cable by cable (`wide/trio: no-loop`, board 880x500px):

    guitar -> tuner     drawn   20.1in  (940,400)->(923,400)->(923,521)->(645,521)->(645,394)->(394,394)
                        cascade 14.0in  (940,400)->(930,400)->(394,400)->(394,394)
    delay -> amp input  drawn   11.4in  (0,394)->(-13,394)->(-13,123)->(-60,123)->(-60,250)
                        cascade  5.1in  (0,394)->(-50,394)->(-50,250)->(-60,250)

The guitar cable dips below the board (y=521 on a 500px board) and comes back. The amp cable runs
127px along the amp face, which the July "fifth pass" fix removed from the cascade.

Mechanisms, all in `lanes/index.ts`:
- Row-end gaps and the external columns connect only through horizontal corridors (250-251,
  271-275), so guitar -> first pedal always detours through one.
- A lone cable sits at the corridor *centre* (477-481); for the corridors above and below the
  rows that centre is off the board.
- External endpoints get no standoff (538-539: `getStandoffPoint` with a null box returns the
  jack), unlike `externalStandoff` in the cascade.

Because the optimizer scores this geometry, its largest dimension (`cableLength` separated the
best candidate from the median on 79 of 173 searched boards) is partly measuring router detours.

Fix, cheapest first: make the guard compare the whole outcome in order - invalid cables,
crossings, lane violations, then length. Both passes stay and scoring still equals drawing, so
this does not reopen the R3 or P1.5 decisions. Then decide whether to repair the corridor
geometry (three items above) or retire it; on this corpus it earns its keep on 2 boards.

## 4. 84% of Optimize time is the A* rung, which draws 0.1% of the cables

- Optimize across the corpus: 8,075ms, of which 6,798ms inside `findPathAStar` (10,705 calls).
- A* produced 2 of 1,962 drawn cables.
- With A* stubbed to fail: 8,136ms -> 1,198ms (6.8x), slowest board 608ms -> 268ms. Drawn result
  worse on 2 boards, better on 2, identical on 212; totals 11,551in/128 crossings -> 11,514in/127.

Why it cannot help: `pathfinding/index.ts:107-132` blocks cells with floor/ceil on an 8px grid,
which closes any gap narrower than about 0.9in. Measured: a straight run through a 14, 20, 24, 28
or 32px gap is legal by `isPathClear`, and A* refuses every one; it first threads at 36px. The
placer packs at 20px side to side and 14px row to row, so A* only ever finds routes around the
outside, and then loses to `perimeter` or fails. Each failure burns up to 10,000 iterations with
a linear open-set scan (221, 227-232, 297).

Fix: either delete the rung, or replace it with an exact search on the sparse grid of obstacle
edges offset by `OBSTACLE_MARGIN` (a few dozen lines per axis instead of 20k cells). The second
option threads every legal gap and would subsume `channel`, `above`, `below` and `safe-lane` too.

## 5. The order search looks at a lexicographic prefix, and re-scores a quarter of it

`layout/index.ts:1227,1413-1482` caps candidates at the first 48 permutations in lexicographic
order. For a group of 5 or more that means the first pedal never changes.

- `rand#1047` (one group of 6 = 720 orders): only orders starting with the same pedal are
  reachable. Optimize returned 181.29; exhaustive best is 175.99. Its answer ranks 145 of 720,
  with 144 strictly better orders beyond index 48.
- Consequence visible in the app: a second click on Optimize found a better board on 2 of 216
  (181.29 -> 175.99, 133.61 -> 133.31). `config-matrix` asserts idempotence but has no group
  large enough to break it.
- 1,235 of 5,147 scored candidates (24%) were exact repeats of an (order, rotations) pair already
  scored: stage 1 re-runs every order on each pass even when rotations did not change, and
  `order === bestOrder` (1290) is an identity check that never matches the first candidate.

Fix: memoize `evaluate` on (order, rotations). Replace prefix enumeration with local search
inside the same budget (adjacent swaps and single-pedal moves from the incumbent), which is not
biased toward the first slot.

## 6. Lane capacity is per corridor, not per stretch of corridor

`lanes/index.ts:381-384,436-454` counts every cable that touches a corridor against its
capacity, wherever along it they run. A row corridor at the designed `ROW_GAP` has capacity 1
for the whole board width.

Repro: two rows 14px apart on a 32in board, one cable hopping rows at each end.

    routed together: ["evicted","lane-routed"]   pressure: capacity 1, demanded 2
    routed alone   : lane-routed, lane-routed
    x-extents      : 135..175 and 1064..1104    (890px apart)

64 cables in the drawn corpus were evicted. This is the `assignLanes` cliff the diagnostics were
added to observe. Fix: assign tracks by interval overlap (the left-edge algorithm from channel
routing) so capacity is the maximum number of *simultaneous* runs.

## 7. Smaller defects

- **Two paths, two answers** (`layout/index.ts:1178` vs `1364`). Same board, a legal hand layout
  the placer cannot reproduce: with no swappable group the headline is "Already optimal - nothing
  moved."; with one swappable pair it is "Could not fit these pedals on this board". The comment
  at 1166-1177 says the search path uses the right rule; it does not count the baseline.
- **A no-op Optimize is recorded as an edit** (`configuration-store.ts:815,859`). On a saved,
  already-optimal board: undo entries 1 -> 2, `isDirty` false -> true, redo stack cleared, pedal
  state unchanged.
- **`console.warn` is reassigned globally during the straddler dry run** (`layout/index.ts:506-512`),
  and the placer warns on every degraded candidate inside a 200-evaluation loop (433, 448).
- **Unverified reachability:** the optimizer builds a pseudo-amp from raw `useEffectsLoop`
  (`layout/index.ts:135`, `routing-cost.ts:152,172`) while the canvas uses
  `useEffectsLoop && amp.hasEffectsLoop` (`derived.ts:160`). `setAmp` keeps them consistent;
  `initConfiguration` (303) does not check. Only matters if a saved row has the flag set against
  an amp without a loop. Not reproduced.

## 8. An observation, not a defect: the search has little to choose between

43 of 216 boards gave the optimizer one candidate or none; the median was 12. Every candidate is
the same greedy construction with a different order or rotation, so `spacing`, `signalFlow` and
`rowAlignment` had a median spread of 0 across candidates - they are properties of the placer,
not choices. If Optimize is to feel smarter, the lever is more *kinds* of candidate (where a row
breaks, which end a short chain packs to, mirrored packs), not more weight tuning.
