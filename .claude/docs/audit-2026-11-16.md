# Code audit, 2026-11-16: Optimize, cable routing, cable display

Scope: the Optimize pipeline end to end (`store.optimizeLayout` -> `calculateOptimalLayoutJoint`
-> greedy placer -> `calculateRoutingCost` -> `routeCablePaths` -> lane router / strategy cascade
/ A*), plus what the canvas and panels show for it. Nothing in `src/` was changed.

Ordered by what it costs to be wrong. Every number below was measured this session by running
the real engine, not read off the code.

## How it was measured

- **Baseline:** `npm test` 548 passed / 4 skipped, `tsc --noEmit` clean, `eslint` clean, `knip`
  clean, before and after the audit.
- **Corpus:** 216 boards. The 66 `config-matrix` scenarios, plus 150 seeded random boards on four
  real board sizes (Classic Jr, Classic 2, Classic Pro, Wide 22) at 45-80% row fill, 4-15 pedals,
  mixed side-jack and top-jack pedals. Each went through normalize -> optimize -> apply (exactly
  as the store applies it) -> derive.
- **NOT in the corpus: the real saved boards.** `dump-configs-offline.js` failed with
  `fetch failed` (no database access from this sandbox). So no figure here is about J$ Home or
  `test`. Re-run the fingerprint on them before acting on a percentage.
- Timing is node, inline, not the browser worker.
- The harness was throwaway vitest files, removed from the repo afterwards. Copies and raw output
  are in the session scratchpad (ephemeral). Each finding says how to reproduce it.

## What held

- 0 of 216 optimized boards had overlapping or off-board pedals.
- 1 invalid cable in 1,962 drawn.
- Scored length == drawn length on every board, when both are given the same pedal array
  (the P1.5 parity holds at the router level).
- Determinism held everywhere it was checked.

## 1. The same board draws two different ways (and Optimize reports the one you do not see)

**Root cause: `cables/routing-strategies.ts:469-480`.** The `channel` rung sorts boxes by top edge
and takes the gap between *consecutive* boxes. Two pedals in one row with different depths (any
rotated pedal, any EQ-200) tie on `top`, so which gap is found depends on the order of the
`placedPedals` array. In one order the real corridor is found; in the other the "gap" lands
inside the deeper pedal, the rung fails, and the cable falls through to A* or the perimeter.

Minimal repro (three boxes, one cable, only the array order differs):

    order A,B,C: strategy=channel  14.3in  (-50,100)->(-50,223.5)->(300,223.5)->(300,300)
    order B,A,C: strategy=astar    19.9in  (-12,100)->(-12,-12)->(300,-12)->(300,300)

**Why it reaches the user: `store/configuration-store.ts:837-844`.** The optimizer scores each
candidate with the array in chain order (`layout/index.ts:1200`). The store then writes new
`chainPosition` values without re-sorting the array. So when Optimize changes the order, the
canvas routes a different array than the one that was scored. Through the real store:

    rand#1057 (Classic Pro, 13 pedals)
    Optimize summary says            after = 40.73
    drawn right after Optimize       73.2in, 2 crossings   (wrap cable goes around the board)
    drawn after normalizeChain()     30.7in, 0 crossings   (pedal state byte-identical)

Any later `normalizeChain` or a save-and-reload (`load-configuration.ts:103` orders by
`chain_position`) re-sorts the array and the cables jump with nothing moved.

Measured: 18 of 216 boards draw differently under a shuffle of the array (8 by more than 0.5in,
worst 45.2in vs 72.6in). 3 of 216 had an Optimize score that the applied board does not have.

### FIXED 2026-11-16 (same day, uncommitted at time of writing)

`freeBandsBetween` in `cables/routing-strategies.ts` merges overlapping y-ranges into occupied
bands and proposes a channel only in the free space between two bands. A union cannot depend on
how ties were ordered. Nothing else changed - the store still does not re-sort, and does not
need to.

Re-measured on the same 216 boards, this time against eight permutations per board (store
order, reversed, six seeded shuffles) rather than the single shuffle above:

| | before | after |
|---|---|---|
| boards that draw differently by array order | 30 | 0 |
| Optimize score != applied board's score | 3 | 0 |
| total drawn length | 11,551in | 11,512in |
| crossings | 128 | 121 |
| invalid cables | 1 | 1 |
| lane violations | 4 | 6 |

**The lane-violation row is a real cost, and it is a separate weakness this fix exposes rather
than one it creates.** Both new violations are on one board (`rand#1047`), which Optimize now
lays out differently (score 181.29 -> 126.58): two cables take the same row corridor, it is too
narrow for two lanes, and they are drawn on the same line for 60px. The cost function has no
term for overlapping runs, so the optimizer cannot see that when it picks the layout. Not chased
here - it is open, and the config-matrix corpus (which asserts zero lane violations) is unaffected.

Regression tests, both run against the old code first to confirm they fail there (7 of 14 red:
`expected 99.20 to be close to 40.73`, `expected 'astar' to be 'channel'`, three matrix boards
differing when the array is reversed):

- `cables/__tests__/routing-order-independence.test.ts` - permutes the pedal array on eight
  matrix boards (three of which were order-dependent) and compares the drawn cables; plus the
  three-pedal repro above in every order of the three.
- `store/__tests__/optimize-draws-what-it-scored.test.ts` - the 13-pedal board through the real
  store: the summary's score equals the applied board's score, and `normalizeChain` does not
  change the drawing.

## 2. The shopping list and the cable total are not the cables on screen

`cables/index.ts:19,223-246` computes every cable's length as straight-line jack distance x 1.2,
rounded up to a standard length. "What to buy" (`cable-list-panel.tsx:77`), the toolbar total
(`board-readout.tsx:57`), the right panel (`right-panel.tsx:73`) and the dashboard
(`dashboard/page.tsx:76`) all read that estimate. The routed path is never consulted.

- 165 of about 1,330 pedal-to-pedal cables were drawn longer than the length the list says to buy.
- Worst: a perimeter cable drawn at 55.4in, listed as a 12in patch cable.
- Board totals disagree in both directions: readout 174in vs 113.2in drawn; readout 60in vs
  75.6in drawn.
- Optimize's own summary ("12in less cable length") is a third number, from routed length.

### FIXED 2026-11-16 (uncommitted at time of writing)

`engine/cables/derive-cables.ts` is now the one derivation of cable length. `deriveCables`
computes topology, routes the cables, then gives each cable the shortest standard length that
covers its route (`purchaseLengthInches`), and returns the exact drawn total
(`drawnLengthInches`). `store/derived.ts` calls it and exposes the total as `cableLengthInches`;
the toolbar CABLE field, the Cables drawer header and the dashboard hero all read that one
number. "What to buy" and the wiring list are unchanged code - they read
`calculatedLengthInches`, which is now the routed purchase length.

Two decisions worth knowing about:
- **No slack factor.** Rounding up to a standard length is the slack. A 7in route lists a 12in
  cable; nothing is multiplied on top.
- **An unroutable (red) cable keeps the straight-line estimate.** Its drawn path is the
  deliberate through-the-pedals L, not a route anyone would cut a cable to.

Same 216 boards (after the finding-1 fix, so the routes differ slightly from the figures above):

| | before | after |
|---|---|---|
| drawn longer than listed, all cables | 430 of 1,962 | 0 |
| ...pedal-to-pedal only | 161 of 1,326 | 0 |
| worst shortfall | 34.0in | 0 |
| listed a size larger than the route needs | 7 | 0 |
| largest gap between CABLE readout and drawn total | 76.4in | 0.00in |
| sum of all listed lengths | 15,504in | 19,140in |

**The last row is finding 3 arriving on the shopping list.** The list now tells the truth about
the drawing, and the drawing is about 50% longer than it needs to be wherever the lane router
detours. Until finding 3 is dealt with, "What to buy" will quote longer cables than a person
would actually run on those boards. That is the honest state - the list and the canvas agree -
but it raises the priority of finding 3.

Tests, the first run against the old derivation to confirm it fails there (all 9 boards red,
e.g. `guitar -> tuner: drawn 20.1in, listed 18in`):

- `cables/__tests__/listed-length-covers-route.test.ts` - reads only what the UI reads; every
  valid cable's listed length covers its route and is the shortest standard length that does.
- `cables/__tests__/derive-cables.test.ts` - the rounding rules, the unroutable fallback, and two
  equalities: the readout equals the sum of the drawn paths, and equals the layout cost
  function's cable length (so the readout and the Optimize summary move together).

## 3. The lane router draws about 50% more cable than the cascade, and wins every tie

`route-cables.ts:348-349` routes each board twice and keeps the lane version unless the cascade
has strictly fewer *crossings*. Length, validity and lane spacing are not compared.

Same 216 final boards, each router on its own:

| | lane router | strategy cascade |
|---|---|---|
| total drawn length | 14,228in | 9,365in |
| fewer crossings on | 28 boards | 88 boards |
| lane violations (runs <9px apart) | 8 | 4 |
| invalid cables | 1 | 1 |

On the 100 boards where crossings tie, the lane version was more than 3in longer on 93 (mean
+19.4in), and on all 93 the cascade had zero lane violations. The cascade was no worse on
crossings, validity and lane spacing *and* shorter on 179 boards; the lane router on 2.

One board, cable by cable (`wide/trio: no-loop`, board 880x500px):

    guitar -> tuner     drawn   20.1in  (940,400)->(923,400)->(923,521)->(645,521)->(645,394)->(394,394)
                        cascade 14.0in  (940,400)->(930,400)->(394,400)->(394,394)
    delay -> amp input  drawn   11.4in  (0,394)->(-13,394)->(-13,123)->(-60,123)->(-60,250)
                        cascade  5.1in  (0,394)->(-50,394)->(-50,250)->(-60,250)

The guitar cable dips below the board (y=521 on a 500px board) and comes back. The amp cable runs
127px along the amp face, which the July "fifth pass" fix removed from the cascade.

Mechanisms, all in `lanes/index.ts`:
- Row-end gaps and the external columns connect only through horizontal corridors (250-251,
  271-275), so guitar -> first pedal always detours through one.
- A lone cable sits at the corridor *centre* (477-481); for the corridors above and below the
  rows that centre is off the board.
- External endpoints get no standoff (538-539: `getStandoffPoint` with a null box returns the
  jack), unlike `externalStandoff` in the cascade.

Because the optimizer scores this geometry, its largest dimension (`cableLength` separated the
best candidate from the median on 79 of 173 searched boards) is partly measuring router detours.

### FIRST STEP FIXED 2026-11-16 (uncommitted at time of writing)

The guard in `cables/route-cables.ts` now compares the whole outcome, in order: invalid cables,
crossings, lane conflicts, length (`routingOutcome` + `compareRoutingOutcomes`). Ties still go to
the lane router. Both passes still run and scoring still equals drawing, so R3 and P1.5 are not
reopened. Lane conflicts rank above length on purpose: otherwise the cascade could win a board
by stacking two cables on one line.

Same 216 boards, after the fixes for findings 1 and 2:

| | before | after |
|---|---|---|
| total drawn length | 11,512in | 9,420in (-18%) |
| sum of listed purchase lengths | 19,140in | 16,812in |
| invalid cables | 1 | 1 |
| lane violations | 6 on 2 boards | 6 on the same 2 boards |
| crossings | 121 | 127 |
| boards drawn by the lane router | 129 | 30 |
| cables drawn by the lane router | 1,064 of 1,962 | 296 of 1,962 |
| cables drawn dashed, "around the board" | 35 | 47 |
| Optimize time, whole corpus | 7,960ms | 8,535ms |

Three rows need reading rather than skimming:

- **Crossings went up by 6, and not because of the guard.** On any one layout the guard takes
  the fewest crossings unless that costs an invalid cable, exactly as before. The rise is the
  optimizer choosing different layouts: with honest lengths, a layout that saves more than 8in
  now beats one with one fewer crossing, because that is what `CROSSING_PENALTY_INCHES` says a
  crossing is worth. If that trade looks wrong on a real board, the weight is the thing to
  change, not the guard.
- **12 more dashed cables, none of them moved off the board.** For all 47 the lane router's own
  path also ran outside the board edge (checked per cable); it simply drew that as a solid line.
  Most are a top-jack pedal in the back row hopping about 1.3in above the top edge. They are now

- **The lane router still wins 30 boards**, on crossings or lane conflicts. It is not dead code.

One existing test had to be rewritten, not relaxed: `lane-router.test.ts` counted cables whose

### Repair or retire: re-measured after finding 4, and the answer is neither yet

The same table as the top of this finding, on the final code (findings 1-4 applied):

| 216 boards | lane router alone | cascade alone | what is drawn |
|---|---|---|---|
| total length | 14,508in | 8,988in | 9,471in |
| crossings | 312 | 200 | 128 |
| lane conflicts | 13 | 5 | 4 |
| invalid cables | 1 | 1 | 1 |

The drawn board beats BOTH routers on crossings, which neither can do alone: the lane router
gives the better picture on 34 boards (33 of them on crossings) and the cascade on 182. Retiring
the lane router would put back 72 crossings - a third of the cascade's own total - to save 483in
of cable on those 34 boards. That is not a trade the cost function would make (a crossing is
priced at 8in; 72 of them is 576in).

What keeping it costs: routing a board both ways takes 2.59x the cascade alone, measured on the
final boards. After finding 4 that is 2.59x of a much smaller number.

So: **do not retire it.** Repairing its geometry (direct column-to-row-end connections, lanes that
hug the near side rather than the corridor centre, a standoff on external endpoints) is still
worth doing - on the 34 boards it wins, it wins while drawing more cable than it needs to, and it
would start winning boards it currently loses on length - but it is now an improvement to a
working part, not a rescue. It ranks below finding 5. The owner has not ruled on this; it is the
audit's recommendation.

## 4. 84% of Optimize time is the A* rung, which draws 0.1% of the cables

- Optimize across the corpus: 8,075ms, of which 6,798ms inside `findPathAStar` (10,705 calls).
- A* produced 2 of 1,962 drawn cables.
- With A* stubbed to fail: 8,136ms -> 1,198ms (6.8x), slowest board 608ms -> 268ms. Drawn result
  worse on 2 boards, better on 2, identical on 212; totals 11,551in/128 crossings -> 11,514in/127.

Why it cannot help: `pathfinding/index.ts:107-132` blocks cells with floor/ceil on an 8px grid,
which closes any gap narrower than about 0.9in. Measured: a straight run through a 14, 20, 24, 28
or 32px gap is legal by `isPathClear`, and A* refuses every one; it first threads at 36px. The
placer packs at 20px side to side and 14px row to row, so A* only ever finds routes around the
outside, and then loses to `perimeter` or fails. Each failure burns up to 10,000 iterations with
a linear open-set scan (221, 227-232, 297).

### FIXED 2026-11-16 (uncommitted at time of writing)

Replaced, not deleted. `pathfinding/sparse-grid.ts` searches a grid made of the lines that matter:
one just outside each pedal's margin on all four sides, one down the middle of any narrow gap,
and the endpoints' own row and column. A flood fill answers "is there a route at all" before the
real search runs, because at this rung the usual answer is no. The dense A*, its shortcuts and
its perimeter fallback are gone from `pathfinding/index.ts` (607 -> 95 lines), along with
`GRID_CELL_SIZE`. The rung keeps the `astar` label and its place in the cascade, so no earlier
rung's picture changes.

Same 216 boards, both runs warmed up:

| | dense 8px A* | sparse grid |
|---|---|---|
| Optimize time, whole corpus | 8,085ms | 1,369ms (5.9x) |
| slowest single board | 651ms | 289ms |
| total drawn length | 9,420in | 9,471in |
| crossings | 127 | 128 |
| invalid cables | 1 | 1 |
| lane violations | 6 on 2 boards | 4 on 1 board |
| diagonal segments drawn | 1 | 0 |
| cables the rung draws | 9 | 5 |
| cables drawn "around the board" | 47 | 49 |

Read it as a speed and honesty fix, not a quality one. The rung draws FEWER cables than before
(5 against 9): the dense A* was finding routes for guitar and amp cables by running outside the
board edge as a solid line, which is the thing `isPathWithinBounds` was written to stop for
on-board cables and never applied to external ones. The sparse grid keeps board-edge lines off
the table for every cable, so those are now drawn dashed by the perimeter rung. On real packed
boards, when the L-paths and the row corridor both fail there is usually no on-board route to
find - which the new rung now says in microseconds instead of 10,000 iterations.

What it can do that the old one could not is thread a real gap. `cables/__tests__/
exact-search-rung.test.ts`, run against the dense A* first: a cable whose only route is a 14,
20 or 28px gap came back `perimeter` there (`expected 'perimeter' to be 'astar'`) and is routed
through the gap now; 36px passed on both, which is the 0.9in limit measured above.

`pathfinding/__tests__/sparse-grid.test.ts` checks "finds a route exactly when one exists"
against an independent oracle - a flood fill over every half-pixel of the board - on 120 seeded
fields (95 routed, 23 sealed, all in agreement), plus the limit by hand: 12px is refused, 12.5px
is found on the one legal line in it, 13px and up are threaded.

## 5. The order search looks at a lexicographic prefix, and re-scores a quarter of it

`layout/index.ts:1227,1413-1482` caps candidates at the first 48 permutations in lexicographic
order. For a group of 5 or more that means the first pedal never changes.

- `rand#1047` (one group of 6 = 720 orders): only orders starting with the same pedal are
  reachable. Optimize returned 181.29; exhaustive best is 175.99. Its answer ranks 145 of 720,
  with 144 strictly better orders beyond index 48.
- Consequence visible in the app: a second click on Optimize found a better board on 2 of 216
  (181.29 -> 175.99, 133.61 -> 133.31). `config-matrix` asserts idempotence but has no group
  large enough to break it.
- 1,235 of 5,147 scored candidates (24%) were exact repeats of an (order, rotations) pair already
  scored: stage 1 re-runs every order on each pass even when rotations did not change, and
  `order === bestOrder` (1290) is an identity check that never matches the first candidate.

### FIXED 2026-11-16 (uncommitted at time of writing)

Two changes in `layout/index.ts`, both inside `calculateOptimalLayoutJoint`:

- **Each candidate is scored once.** `evaluate` is keyed on the order plus the rotation of the
  pedals allowed to turn; a repeat is a map lookup and no longer spends the budget.
- **A space too big to list is walked group by group.** When every order fits under 48 they are
  all tried, exactly as before - which is every board in the config-matrix corpus. Otherwise the
  search takes each swappable group in turn, scores every arrangement of it with the rest of the
  chain held still (every permutation up to four pedals, single swaps above that), keeps the
  best if it is strictly better, and goes round until a whole round changes nothing.

Same 216 boards, on the code after findings 1-4:

| | before | after |
|---|---|---|
| candidates scored | 4,773 | 3,328 |
| ...of which repeats | 1,210 (25%) | 0 |
| Optimize time, whole corpus | 1,395ms | 974ms |
| boards a second Optimize moves | 2 | 0 |
| sum of final scores, all boards | 12,306.1 | 12,243.1 |
| sum of final scores, the 11 boards with more than 48 orders | 976.6 | 913.6 |

The 205 boards with 48 orders or fewer came out identical. Of the 11 others: 8 better, 2 the
same, **1 worse** - `rand#1058` (groups of 3/2/3, 72 orders) went from 75.04 to 78.44. The old
prefix covered 48 of its 72 orders and the better one was among them; the group-by-group walk
stops at an order no single group can improve, and that is not it. Raising the list-everything
limit from 48 to 72 or 144 would make that board exhaustive, but it is a tuning decision with
its own cost (the rotation stage re-walks the list at each new rotation, out of the same 200
evaluations) and was left alone.

**What was tried first and thrown away:** a swaps-only walk. It fixed the repeats and the second
click and made one board far worse - `rand#1035` (groups 2/4/2/2/2/2) stuck at 235.15 against
the 81.82 the old prefix had found, because the good order is two swaps inside the group of
four away and the first of them alone makes things worse. Group-by-group gets 77.52 there.

`layout/__tests__/order-search.test.ts` pins three boards from the sweep (one group of six; four

## 6. Lane capacity is per corridor, not per stretch of corridor

`lanes/index.ts:381-384,436-454` counts every cable that touches a corridor against its
capacity, wherever along it they run. A row corridor at the designed `ROW_GAP` has capacity 1
for the whole board width.

Repro: two rows 14px apart on a 32in board, one cable hopping rows at each end.

    routed together: ["evicted","lane-routed"]   pressure: capacity 1, demanded 2
    routed alone   : lane-routed, lane-routed
    x-extents      : 135..175 and 1064..1104    (890px apart)

64 cables in the drawn corpus were evicted. This is the `assignLanes` cliff the diagnostics were
added to observe.

### FIXED 2026-11-16 (uncommitted at time of writing) - and it bought nothing you can see

`assignLanes` now measures a corridor by its busiest STRETCH: the most runs that want the same
part of it at once. A corridor is over capacity only when that exceeds its lanes, eviction takes
the shortest run out of the pile-up, and where a corridor has more cables than lanes but they do
not all meet, the ones that do not meet share a lane. Each run's extent is taken conservatively
(a run ends on the cable's lane in the NEXT corridor, which is not chosen yet), so two runs are
only called apart when they are apart whatever lanes their neighbours get. `pressure.demanded`
now reports the pile-up, not the head count.

The repro above now reads `["lane-routed","lane-routed"]`, pressure `[]`.

Same 216 boards, on the code after findings 1-5:

| | before | after |
|---|---|---|
| cables evicted on the final boards | 49 from 14 corridors | 16 from 7 |
| cables the corridor router serves | 1,858 of 1,962 | 1,888 |
| boards the lane router gives the better picture on | 34 | 34 |
| drawn: total length | 9,438in | 9,434in |
| drawn: crossings | 128 | 129 |
| drawn: lane conflicts / invalid | 4 / 1 | 4 / 1 |
| sum of final scores | 12,243.1 | 12,247.6 |

**Read the bottom five rows: the drawn boards did not change.** Two thirds of the evictions are
gone and nothing a user sees is better for it. The reason is the guard from finding 3 plus the
cascade behind it: an evicted cable was already being handed to a router that usually drew it
well, so seating it in the corridor instead is a sideways move. The accounting was wrong and is
now right; that is all this fix can honestly claim. It is worth having for the corridor-geometry
repair, where a lane router that drops cables for no reason would be the first thing in the way.

**What was built first and measured worse:** sharing a lane wherever two runs do not meet, not
only where the alternative is eviction. It cut evictions identically and raised the lane
router's own crossings from 307 to 410, dropped the boards it wins from 34 to 27, and pushed
drawn crossings from 128 to 138. Collapsing two runs onto one line frees a lane nobody needed
and throws away the ordering - which side of its neighbours a run sits on is what keeps its
legs from crossing them. So a corridor with room still gives every cable its own lane, and that
is pinned in the tests.

`lanes/__tests__/lane-capacity.test.ts`, run against the old assignment first: 3 of 4 fail
(`expected ['evicted','lane-routed'] to deeply equal ['lane-routed','lane-routed']`); the fourth
is the unchanged-behaviour pin and passes on both, as it should.

## 7. Smaller defects

All four FIXED 2026-11-16 (uncommitted at time of writing). Each test was run against the old
code first.

- **Two paths, two answers** (`layout/index.ts`, the search path's return). Same board, a legal
  hand layout the placer cannot reproduce: with no swappable group the headline was "Already
  optimal - nothing moved."; with one swappable pair it was "Could not fit these pedals on this

## 8. An observation, not a defect: the search has little to choose between

43 of 216 boards gave the optimizer one candidate or none; the median was 12. Every candidate is
the same greedy construction with a different order or rotation, so `spacing`, `signalFlow` and
`rowAlignment` had a median spread of 0 across candidates - they are properties of the placer,
not choices. If Optimize is to feel smarter, the lever is more *kinds* of candidate (where a row
breaks, which end a short chain packs to, mirrored packs), not more weight tuning.

### What the fixtures missed

**1. My finding-3 guard was wrong on a tie, and J$ Home showed it.** The comparator's last step
was bare length. One J$ Home layout routed both ways tied on invalid cables, crossings and lane
conflicts: lane router 65.1in with every cable on the board, cascade 54.1in with three cables

such cable, so the optimizer scored that layout 118.1 instead of 89.1, passed over it, and
settled on one drawing **78.7in where `main` had drawn 65.1in**. Fixed (uncommitted at time of
writing): the last step now compares what the cost function would charge - length plus

`cables/routing-strategies.ts`. Crossings and lane conflicts still rank above it and are not
priced. J$ Home is back to 65.1in. On the 216-board corpus:

On a full board most candidate orders do not pack. Each pedal that finds no row is handed to
the placer's last resort, which tests every quarter-inch position on the board against every
other pedal - 64 x 128 positions x 21 boxes - and then again at three spacings. That runs for
each such pedal, in each of about five retry attempts, for each of 78 candidates. Routing was
never the cost here.

**OPEN, not started.** The scans can be made cheap without changing their answers: for one row
of positions, the blocked x-ranges follow directly from the boxes that overlap that row, so the
first free quarter-inch step can be found from the box edges instead of by trying all 128. The
result must be byte-identical placements, which the corpus and both real boards can prove.
